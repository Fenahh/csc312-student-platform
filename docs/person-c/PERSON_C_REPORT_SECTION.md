# Module Implementations: Search & Discovery (Person C)

The Search and Discovery module was developed for the Commons student resource portal using Flask, SQLAlchemy and a SQLite database. Students can browse shared study resources, search by title, description or module code, and narrow results to a specific university module. The server normalizes each search term, limits it to 100 characters and uses SQLAlchemy to construct parameterized, case-insensitive `ILIKE` conditions. SQL wildcard characters are escaped so user-supplied search text is interpreted literally. Module filtering uses an exact comparison against an uppercase course code, and users can combine a keyword query with a selected module.

The Browse interface displays responsive cards containing a resource title, abbreviated description, module tag, contributor and date. Module tags provide a direct route to resources from the same course. Clearly labelled search controls, an all-modules selection, a result count and a helpful empty state support navigation without requiring technical knowledge. Bootstrap grid classes adapt the card layout across mobile and desktop viewports. Search results use a stable newest-first order and are limited to twelve per page; pagination preserves active filters. An indexed `module_code` column supports efficient equality-based module filtering. Existing records are retained during migration and marked `UNASSIGNED` until classified. These design decisions emphasize usability, safe query handling and maintainable feature separation.

## Non-Functional Requirements: Usability and Performance

The search interface uses semantic form labels, keyboard-accessible links and buttons, responsive Bootstrap grid rules, visible result counts and descriptive fallback text. Search input is length-limited and SQLAlchemy parameter binding prevents the query string from being interpolated as raw SQL. The catalogue retrieves twelve ordered records per page, rather than rendering the entire result set. An index supports exact module-code filtering. Keyword substring searches can still require scans; no latency threshold has been measured or verified. Formal claims about response time should be made only after testing on the team's final dataset and deployment environment.
